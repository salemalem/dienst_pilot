# ADR-012: C3 serving, the promotion rule, and dataset identity without DVC

- Status: Accepted
- Date: 2026-10-22
- Phase: 8a (C3 absence forecaster)
- Amends: ADR-007 (item 5, DVC)

## Context

C3 is the first trained component. It needs a defined way to be trained, tracked, promoted and served; the API must not grow a training stack; and ADR-007 deferred DVC to this phase.

## Decision

1. **Promotion rule before the run.** `ml/absence_forecast/PROMOTION_RULE.md` is committed before any model is fitted; its hash is recorded in `eval/results/c3.json` and a test fails if it changes after the run. The best baseline is chosen on 2022 to 2024 cross-validation, the challenger is judged once on the held-out 2025. If the challenger fails, the baseline stays champion and every surface says so.
2. **Registry for the record, a bundle for serving.** Candidates are tracked and registered in a local MLflow store (SQLite, `ml/mlflow/`, git-ignored). `eval/run_c3_eval.py` sets the alias `champion` and exports that candidate to `ml/absence_forecast/artifacts/champion/` (JSON, plus a text file for LightGBM), which is committed. The API loads only that bundle with numpy and LightGBM; an import-linter contract forbids it from importing `mlflow`, `statsmodels` or `dienstpilot_ml.training`. A test checks that the bundle's hash equals the one in `c3.json`.
3. **Deterministic training.** Fixed seeds, LightGBM `deterministic`, `force_row_wise` and one thread. A retrain reproduced the committed bundle hash on the machine that produced it; CI does not retrain (floating-point results can differ between platforms), it checks the committed hashes.
4. **The forecaster port takes a context.** `AbsenceForecaster.forecast(days, history, context)`; `ForecastContext.as_of` comes from the demo clock, never from system time, and the forecast origin is the day before it. Holidays, school holidays and night shifts are passed in by the application layer, so the engine imports no context.
5. **Package layout.** One workspace package `dienstpilot-ml` (`ml/src/dienstpilot_ml/{features,absence_forecast,training}`). Its base dependencies (numpy, LightGBM) are what the API needs; MLflow, statsmodels and polars are the `train` extra. Non-code files (rule, bundle, notes) stay in `ml/absence_forecast/`.
6. **No DVC (amends ADR-007 item 5).** The generator's `manifest.json` already records the seed, the generator version and a SHA-256 per file, and the dataset is regenerated byte for byte from the seed. Training re-checks every file it reads against the manifest, and `c3.json` records the manifest hash and the hash of each file read. A DVC remote here could only be a local folder that nobody else can pull from, and it would add a second source of truth. DVC is revisited if feature snapshots or models become too large to regenerate, or when a shared remote exists. Docs that named DVC (ARCHITECTURE §8 and §13, CLAUDE.md, PLAYBOOK) now describe the manifest hashes.

## Consequences

- The result file belongs to a data identity, the C3 source hash, the rule hash and the served bundle hash; `eval/tests/test_c3_results_are_current.py` fails if any of them drifts from `c3.json`.
- The served model is whichever candidate the rule picks, which may be a baseline. That is reported, not hidden.
- New dependencies: `lightgbm`, `mlflow-skinny`, `statsmodels`, `scipy` and their transitive packages; three transitive packages were pinned below their latest release (`constraint-dependencies` in the root `pyproject.toml`) to respect the 7-day release-age rule.
- The served model is not refitted on 2025, so the published metric describes it exactly; refitting belongs to a retraining cycle with a new held-out period.
