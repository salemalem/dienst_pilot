# Model card: C3 Absence Forecaster (Ausfallprognose)

Status: built and evaluated on synthetic data. Nothing here describes a real department, and no number below has been measured on real staff.

## Intended use

Estimate how many people of the department will be absent (sick) on each of the next 1 to 42 days, with an 80 % prediction interval. The planner dashboard shows it as the band in the coverage view (W1), and it supports the recommendation to schedule reserve capacity on high-risk days. It never changes a roster.

## Out-of-scope uses

- Any prediction about an individual person. The model has no individual-level input and none can be added without a new ADR and works-council review (ADR-003).
- Using it as a diagnosis, a sick-leave control tool or a performance measure.
- Forecasts for other departments or for real data: it was trained on one fictional department's synthetic history.
- Horizons beyond 42 days (the adapter refuses them).

## Data

- Synthetic: `data/synthetic/v1`, fictional "Klinik für Innere Medizin, Klinikum Musterstadt" (`synthdata/ASSUMPTIONS.md`). The identity of the exact files read is recorded in `eval/results/c3.json` (manifest hash and a SHA-256 per file); training re-checks each file against the manifest.
- Target: department-level count of absent (sick) people per day, built from absence intervals. Sickness is stored without diagnosis.
- Tables read: absences, public holidays, school holidays, published rosters (night shifts). Training code never reads the generator's ground truth, and a test fails if code under `ml/` refers to it.
- Training and model selection: 2021 to 2024. Held-out test: 2025. No random splits.

## Features (one definition, `ml/src/dienstpilot_ml/features/absence.py`)

Forecast horizon, weekday, month, day-of-year harmonics, public holiday, school holiday (all of the target day); absence level over the last 7, 28 and 91 days, the count on the origin day, the same weeks one year earlier; night shifts in the last 7 days. All are department aggregates. Tests check that the features of an origin do not change when data after the origin changes, and that the builder accepts no staff identifier.

Not used, on purpose: the respiratory-illness index of ARCHITECTURE §9 (in this repository it exists only in the ground truth, which training must not read; in a real deployment it would be public surveillance data) and department headcount (28 positions are always filled, so it carries no information). No protected attribute is a feature.

## Models and procedure

- Baselines: seasonal naive (mean of the same weeks 1 or 2 years back, window chosen by cross-validation), Poisson GLM, negative-binomial GLM.
- Challenger: LightGBM, Poisson objective, hyperparameters tuned on the 2022 and 2023 folds only; deterministic mode, one thread, fixed seed.
- Intervals: split conformal, 80 %, scaled absolute residuals per horizon bucket (1–7, 8–21, 22–42 days), calibrated on the out-of-fold forecasts of the 2024 folds. Counts are discrete, so intervals tend to over-cover.
- Rolling-origin cross-validation: six expanding folds of six months over 2022 to 2024; training rows end before each fold's first test origin.
- Promotion: the rule in `ml/absence_forecast/PROMOTION_RULE.md` was committed before any model was fitted. The registry alias `champion` goes to LightGBM only if it passes every check on 2025; otherwise the best baseline (chosen on cross-validation, not on 2025) keeps it.
- Tracking: local MLflow store (`make train`), registered model `c3-absence-forecaster`. The API serves a committed bundle (`ml/absence_forecast/artifacts/champion/`) and never imports MLflow; a test checks that its hash equals the one in `c3.json`. Training is deterministic: a retrain reproduced the same bundle hash.

## Limitations

- Synthetic data: the seasonal waves, episode lengths and noise are simulation inputs. Good results here say that the pipeline works, not that real absences are this predictable.
- Low counts (about one absent person per day): MAE differences between models are small, and one test year gives a noisy comparison. Cross-validation and the 2025 test ranked the models differently, which the promotion rule handles by design; no model was re-tuned after seeing 2025.
- The cross-validation mean is dominated by the earliest fold, where a model has only about nine months of history.
- Conformal calibration uses the 2024 out-of-fold forecasts, not data from the served model's own training period; coverage on 2025 is reported in the table above.
- The served model was trained on 2021 to 2024 and is not refitted on 2025, so the published numbers describe exactly the served model. In a monthly retraining cycle the window would move.
- The truth-recovery check uses the generator's hazard, which ignores two second-order effects of the simulation (nobody falls sick while on leave, nobody already sick falls sick again); see `eval/src/dienstpilot_eval/c3_truth.py`.
- Night-shift load is read from published rosters (as planned), the same definition in training and serving.

## Fairness and privacy considerations

Aggregate department × day only; no individual absence prediction, no per-person feature, no protected attribute. Colleagues see only "absent"; this model adds no new individual-level information. Forecast errors affect planning of reserve capacity, never an individual's roster or evaluation.
